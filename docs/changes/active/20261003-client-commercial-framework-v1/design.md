# 商业客户端通用框架设计

## 1. 勘察结论

`Client/GameFramework/` 已有可复用基础：

| 领域 | 当前基础 | 主要缺口 |
|---|---|---|
| 运行时 | GameClient、Builder、模块宿主、服务注册、事件、计时、流程机、日志与性能统计 | 明确跨异步边界的线程派发；启动中销毁和关闭收敛 |
| UI 与表现 | 窗口层级、焦点、模态暂停、绑定、Presenter、实体池、场景和音频门面 | 输入、资源生命周期统一、真实 Unity 适配与前后台行为 |
| 内容与数据 | 配置、数据表、本地化、设置、资源合同、下载队列 | 版本清单、完整性验证、原子更新、版本化存档与迁移 |
| 联机 | `ITransport`、`IMessageCodec`、消息路由、心跳、重连 | 真实传输和协议由项目或后续供应商适配；事件线程语义需统一 |
| 商业服务 | 尚无统一平台服务合同 | 账号/平台、权限/同意、支付/广告、远程配置、分析/崩溃/性能服务 |

现有 `DownloadService` 是下载任务调度器，不是更新事务；`MemorySettingsStore` 是偏好设置，不是存档系统；示例网络与大多数平台服务是模拟实现，不能描述为线上能力。另有 CAP-21~26 客户端能力草案：宿主、UI、输入、场景表现、更新器和音频。它们作为边界参考，必须映射到现有门面，禁止平行复制宿主、UI 管理器或实体生命周期。

当前代码的异步实现还需要专项核验：模块初始化/关闭及下载路径在等待后使用 `ConfigureAwait(false)`，而下载完成与进度回调会修改服务状态并触发事件。商业模块设计前应由测试确认现行线程行为，并统一异步结果回到框架线程的方式。

## 2. 方案比较

### 方案 A：继续把所有能力放在一个服务类中

接入简单、工程数量少，但账号、存档、支付、广告和遥测会形成互相依赖的巨型门面，错误处理、隐私门控和测试边界难以独立验证。不采用。

### 方案 B：每个供应商和每个能力都新建程序集

隔离性强，但在目标平台与厂商未确定时会产生大量薄工程和过早稳定的程序集边界。供应商差异也不应渗入核心。不作为当前实现方式。

### 方案 C：沿用 Core / Services / UI / Unity 分层，按能力域拆服务

核心保留平台中立合同；Services 每个能力域提供小型服务门面；Unity 和供应商代码以适配器注册；同一合同配有确定性模拟实现用于自动化测试。该方案既复用现有代码，也允许业务项目按需注册能力，作为推荐方案。

## 3. 分层与装配

```text
业务模块
  ├─ 账号 / 平台游戏服务 / 隐私 / 支付 / 广告 / 通知与归因
  ├─ 输入 / UI / 场景与实体 / 音频
  ├─ 存档 / 内容更新 / 远程配置
  └─ 分析 / 崩溃 / 性能诊断
          ↓ 只依赖合同与服务门面
Core：GameClient、模块生命周期、服务注册、事件、帧泵、主线程派发
          ↓
Services：可替换的服务合同、流程实现与模拟实现
          ↓
Unity / 供应商适配：平台 API、文件/资源系统、商店、广告、遥测 SDK
```

不增加 Share 或 Server 依赖，不将外部 SDK 引入 `Core`、`Services` 或 `UI`。业务可通过 Builder 显式注册平台适配；未注册能力时启动诊断应指出缺少的服务，不静默使用模拟实现作为线上默认值。

## 4. 能力范围

| 能力域 | 服务职责 | 核心约束 |
|---|---|---|
| 宿主与调度 | 线程派发、前后台状态、启动/退出取消、后台任务收敛 | Unity API 和业务生命周期回调只在框架主线程执行；I/O 可后台运行 |
| 平台与账号 | 平台能力查询、登录/登出、账号状态、成就/排行榜入口、短期会话凭据句柄 | 核心不持久化访问令牌、不输出凭据；重登与取消结果明确 |
| 隐私与权限 | 同意状态、权限请求、撤回通知 | 分析、广告和归因先检查同意；未同意时不发送个人数据 |
| 支付与广告 | 商品查询、购买、恢复购买、广告加载/展示结果 | 购买回执交可信验证方；核心不授予货币或物品；广告奖励由游戏规则决定 |
| 平台触达 | 推送通知、深链、安装归因结果及应用前后台通知 | 事件在框架线程派发；归因与广告标识服从同意；不定义业务收件箱协议 |
| 输入 | 设备输入映射为动作，支持 UI 消费和动作上下文 | 平台设备与玩法命令解耦；UI 优先消费，避免同一输入重复触发 |
| 存档与偏好 | 版本化存档、迁移、原子写入、完整性/保护扩展点；偏好与游戏进度分离 | 客户端存档可篡改，不作为联网权威；凭据和支付回执不进入普通存档 |
| 内容更新 | 清单与资源版本、下载协调、哈希/签名校验、暂存、原子应用、回滚 | 只有验证通过的暂存内容可切换为当前版本；更新器复用下载代理但不等同下载服务 |
| 远程运营 | 缓存配置、默认值、类型校验、功能开关、实验分组及公告/活动入口 | 只影响可降级的客户端表现，不能改变服务端权威规则或承载玩法协议 |
| 可观测性 | 分析事件、性能计数、崩溃与日志出口、队列刷新 | 服从隐私同意；敏感字段默认过滤；供应商传输失败不得阻塞帧循环 |
| 既有表现服务 | 扩展现有 UI、场景、实体、资源和音频服务 | 延续当前门面；租约/句柄可释放；应用后台行为一致 |

CAP-21~26 与此范围映射为现有宿主扩展、UI 扩展、输入新增、实体/场景分层、独立内容更新器、音频扩展，不单独创建一套能力管理框架。

## 5. 跨模块合同

1. 纯逻辑合同维持 `netstandard2.1` 与当前 Unity 兼容语言版本；Unity 类型只出现在 `Unity/` 适配层。
2. 服务异步操作携带 `CancellationToken`，返回明确结果或有类型的失败；取消不是普通业务失败。
3. 公开事件和生命周期回调由框架线程派发；适配器可在后台完成 I/O，但必须通过注入的派发器交还结果。线程检查在开发与测试构建中可启用。
4. 有界派发队列区分必达调用和尽力而为通知：必达调用队列满时立即以明确的背压错误结束，不得静默丢弃；尽力而为通知可拒绝并增加丢弃计数。已接收调用在关闭时必须完成或以明确取消/关闭错误结束。
5. 关闭顺序为停止接收新业务请求 → 取消在途平台/I/O 操作 → 在限时内排空已接收的必达回调 → 逆序关闭模块。排空超时必须结束剩余等待者并记录诊断，不得无限等待或跨线程直接执行 Unity 回调。
6. 模块启动被取消时，宿主用独立且有时限的清理令牌回滚已初始化模块；不复用已取消的启动令牌。清理异常记录后继续清理其余模块，最后保留原始取消结果。
7. 每个生产合同可注册模拟实现；模拟实现不得自动成为生产配置，Demo 显式选择模拟模式。
8. 日志、遥测和异常诊断不得携带令牌、完整支付回执、原始账号标识或未经允许的个人信息。

## 6. 关键流程

### 启动

宿主建立框架主线程派发器 → 注册选定的平台和服务适配 → 初始化模块依赖 → 加载本地配置/存档元数据 → 可选运行内容更新 → 报告能力缺失或降级 → 进入首个业务流程。更新未通过验证时不得应用半成品；账号或遥测服务不可用不应阻止离线可运行部分，除非项目显式配置为强制能力。

### 存档

游戏模块生成带数据格式版本的数据 → 编码为存档信封 → 可选保护器处理 → 存储适配器写入临时记录并校验 → 原子切换当前记录。读取时校验信封、逐版本迁移并在成功后提交；损坏或未知版本保留原记录并返回可诊断错误。联网游戏进度仍由服务端裁决，本地快照仅作为缓存/离线队列。

### 支付

业务请求商品 → 平台适配器执行购买 → 返回带稳定平台交易标识的结果和不透明回执 → 业务层转交可信验证接口 → 验证成功后业务或服务端授予权益 → 平台交易确认。重复回调、进程重启恢复和恢复购买均以同一交易标识幂等重交验证，验证前不确认消耗型交易。模拟适配只模拟状态与结果，不生成真实凭据，也不直接修改游戏进度。

### 内容更新

读取当前资源版本 → 获取带签名清单 → 校验规范化签名内容、应用/平台标识、有效期、受信密钥及单调序号 → 比对内容块 → 下载到暂存区 → 校验每块完整性 → 写入新版本索引 → 原子切换当前索引。签名固定为 ECDSA P-256、SHA-256、64 字节 IEEE P1363 编码（`r || s`，各 32 字节无符号大端整数）。信任根公钥随应用包或平台可信配置固定；密钥轮换须由当前受信密钥签发并允许有限重叠期，生产信任存储须在进程重启后恢复已接受的轮换状态；当前 `EcdsaContentManifestTrustStore` 是进程内实现，只适合测试和无头演示。旧序号清单拒绝，除非更高序号的签名恢复指令明确授权回退。客户端本地序号只能降低意外回放风险，不能抵御设备完整性被攻破；联网服务仍须执行最低客户端版本策略。失败保留旧版本；启动确认新版本无法读取时可恢复前一快照且保留最高序号。程序集热更与 CDN 策略不在本目标内。

## 7. 失败与降级

| 场景 | 行为 |
|---|---|
| 主线程派发队列关闭或溢出 | 等待中的必达调用以明确背压/关闭错误结束；尽力通知返回拒绝并计数，不在任意线程直接调用 Unity API |
| 已接收的关键派发等待关闭或排空超时 | 按关闭协议完成排空，或以明确取消/关闭错误结束等待者；不得遗留永不完成的任务 |
| 账号/商店/广告平台不可用 | 返回平台不可用或取消结果；由业务流程决定重试或降级 |
| 支付事件重复、恢复或验证暂不可用 | 以稳定交易标识幂等重交；平台交易在可信验证成功前保持可恢复，不重复授予权益 |
| 用户撤回隐私同意 | 停止相关新采集，通知适配器清理可清理队列；不阻塞游戏运行 |
| 存档格式未知或迁移失败 | 保留旧数据、拒绝覆盖并提供恢复诊断 |
| 更新签名/哈希失败、清单过期/回放或暂存写入失败 | 不切换资源版本；可重试下载或继续使用旧版本 |
| 遥测/崩溃出口失败 | 有界队列与重试；不得阻塞帧更新；满载按策略丢弃并计数 |
| 模块初始化失败 | 沿用现有逆序回滚；可选能力按声明降级，必需能力使启动失败 |

## 8. 验收要求

1. Core、Services、UI、Demo、Tests 仍能按现有 solution 构建；Unity 类型不会进入纯逻辑工程。
2. 测试证明所有生命周期和 Unity 相关事件都通过框架线程派发；后台进度事件、取消、队列满/关闭、排空超时、启动回滚和关闭竞态有回归覆盖。
3. 测试覆盖账号取消/失效、游戏平台服务不可用、隐私未同意/撤回、支付等待验证/重复回执/恢复购买、广告失败、推送/深链派发、输入 UI 消费、远程配置非法值回退。
4. 存档测试覆盖版本迁移、损坏、未知数据格式版本、写入中断、原子替换、保护器缺失及客户端数据不可信边界。
5. 更新测试覆盖规范化签名内容、信任密钥轮换、清单过期/序号回放、明确授权回退、坏块重下/失败、断点继续、应用中断、旧版本回滚与幂等重跑。
6. 分析/崩溃/性能测试覆盖同意门控、敏感字段过滤、有界队列、出口失败不阻塞帧泵。
7. Demo 展示模拟平台登录、同意设置、游戏平台服务、深链事件、配置读取、购买验证委托、存档迁移、内容更新和遥测门控的完整路径。
8. Unity 编辑器验证如因无 Unity 工程无法执行，证据保持明确缺口，不宣称 Unity 生产接入已验证。

## 9. 已确认决策

用户已确认本次采用平台中立合同与确定性模拟实现，具体供应商 SDK 留待后续适配包。以下推荐决策作为本次实现约束：

1. **线程模型**：所有框架回调固定回主线程；有界队列满时必达调用明确失败、尽力通知可拒绝并计数；关闭限时排空且所有已接收调用最终完成或明确取消。
2. **启动清理**：启动取消后以独立有时限的清理令牌回滚，不复用已取消的启动令牌；原始启动取消结果优先保留。
3. **支付信任边界**：交易带稳定标识，重复与恢复购买幂等；客户端只向可信验证方转交回执，不授予游戏内权益，验证前不确认消耗型交易。
4. **存档语义**：使用版本化信封、逐版迁移、原子替换；本地数据不可信，保护器为适配接口，不自行发明密钥管理。
5. **清单信任与防回放**：规范化签名内容覆盖应用/平台、资源版本、序号、有效期与块哈希；信任根随应用受信配置提供，轮换由当前密钥签名并设重叠期；过期或旧序号拒绝，回退必须是更高序号签发的明确恢复指令。
6. **目标平台**：沿用现有 Unity + `netstandard2.1` 核心，不选择或引入具体平台、商店或 SDK。

支付合同必须使用稳定的供应商交易标识作为幂等键；验证器可重复接收相同交易，业务权益仍由可信验证方决定。更新清单必须定义可规范化签名字节、固定信任根、有效期、单调序号和由当前信任密钥签发的轮换/恢复规则。框架线程派发必须对队列满、关闭及排空超时给出最终完成结果；实现不得把未完成的等待者遗留到关闭之后。

## 10. 范围、风险与回滚

只修改 `Client/GameFramework/` 与本变更工件；不修改 Share、Server、GAS、供应商 SDK 和适配生成文件。实施按照宿主线程/生命周期、服务合同与模拟实现、存档/更新事务、Demo 与验证分段；每段保留可构建状态，既有服务行为用回归测试保护。

高风险点为网络协议与支付/账号安全边界、存档版本迁移、更新清单信任与防回放、更新原子性和用户隐私。无具体供应商和服务端协议时只实现客户端合同与模拟流程，不声明真实支付、认证、云存档或线上遥测可用。若发现迁移/回滚不满足验收，保持旧实现与 `active` 状态，不切换存档或内容路径。
