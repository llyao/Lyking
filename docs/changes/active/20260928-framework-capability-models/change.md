# 基础框架能力模型体系

## 解决什么问题

框架第一个切片（模块管理中间件）已经落地并整理完毕，但框架其余基础能力目前散落在 `20260919-hydra-game-framework/design.md` 的各章节里：时间、随机、快照、回放合同在 4.3 节，消息元数据在 4.4 节，资源租约在 3.8 节，身份和核心对象在 4.1 节。没有一份文档按顺序回答三个问题：

1. 这个基础框架**一共有哪些能力**？哪些已落地、哪些已定义未落地、哪些还没定义？
2. 每个**能力模型**长什么样（核心对象、合同形状、不变量、失败语义）？
3. 每个能力在**不同情况**（Headless 测试、单机、联机权威、在线多 World）下怎么用？

本文把这些能力整理成一个有序的能力地图（CAP-00 至 CAP-20，五个能力域），逐个给出能力模型卡和使用方案矩阵，作为后续每个能力切片的设计索引。设计本身不写实现代码。

## 当前状态

`draft`。能力地图、四种标准用况和全部能力模型卡已成形；待定选择（下一切片起点）未经用户确认，不得进入 `ready`。

## 完成后应看到什么

- `design.md` 给出五个能力域、21 个能力编号（其中 19 张完整能力卡，另含 CAP-00 已落地事实描述与 CAP-13 后置占位），每个能力卡含：解决的问题、核心对象、关键不变量、失败语义、使用方案矩阵、前置依赖、验收证据形式。
- `drafts/` 下 28 份**逐能力详细设计草稿**（核心通用 CAP-01~12、14~20 + 客户端 CAP-21~26 + 服务器 CAP-27~30）：合同形状（C# 签名）、关键设计决策（含备选与推荐）、不变量、失败语义、U1–U4 使用方案、验收证据与**审核决策点**（编号问题，供逐份拍板）。审核进度见 `drafts/README.md`。
- 四种标准用况（U1 Headless 测试、U2 单机、U3 联机权威、U4 在线多 World）与能力启用矩阵，与顶层 `20260919-hydra-game-framework/design.md` 4.6 Profile 兼容矩阵一致，不引入新口径。
- 后续每个能力切片开工时，从本文对应能力卡出发细化，不再重新盘点。

## 验收方式

- `route` 确认领域与风险；`validate` 工具门禁通过。
- 能力编号、Profile 名称、生命周期序列与 `20260919-hydra-game-framework/design.md`（3.8、3.9、4.1–4.6 节）和 `20260928-module-manager-tidy/change.md` 的权威口径交叉核对一致，无新矛盾。
- 每张完整能力卡（CAP-01~12、CAP-14~20）的使用方案覆盖至少两种标准用况，Profile 类卡（CAP-11、12）与不可用用况以显式点名方式标注"不适用"；CAP-00 只描述已验证事实，不新增承诺；CAP-13 为后置占位，按约定不展开。
- 设计阶段不修改 `Share/` 下任何代码文件。

## 范围与非目标

范围：本变更目录内的设计文档（含 `drafts/` 逐能力草稿，覆盖核心通用、客户端与服务器核心模块）；对既有能力（模块管理）的事实性描述。

非目标：不实施任何能力；不改变 `20260919-hydra-game-framework/design.md` 已确认的决策（VContainer 物化、混合模块模式、依赖 DAG）；不替代顶层设计的第 4 章核心对象定义；不引入 Player/Combat 等产品玩法词汇；Unity 版本、样例、ECS 策略沿用顶层变更的待确认项，不重复决策。

## 风险与回滚

风险：能力卡与顶层设计文档口径漂移（以顶层 design.md 为权威，本文只做索引与细化）；能力粒度切得过细导致切片过多（通过落地顺序一节合并为六个切片控制）。

回滚：纯新增文档，按目录删除即可；不触及代码、协议和持久化。
