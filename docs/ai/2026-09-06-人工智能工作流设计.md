# Lyking 多平台人工智能工作流设计

> 状态：已批准
> 日期：2026-09-06
> 适用项目：Lyking
> 第一版技术边界：Unity、C#、Codex、Claude Code、Gemini

## 一、背景与结论

Lyking 当前处于项目初期，仓库只有 `Art`、`Client`、`Server`、`Share`、`Tool` 五个一级领域目录。工作流需要在小团队阶段保持低摩擦，同时为后续多人、多代理和跨领域并行预留确定性治理能力。

本设计参考以下体系，但不直接复制任何一个体系：

- Hydra：借鉴上下文路由、文档权威层级、薄技能入口、确定性工具、平台适配和外部技能治理。
- `eo-skills`：借鉴三段主流程、轻量变更记录、风险信号升级和证据面。
- `ospec`：借鉴轻量变更与受控目标分离、持久状态、确定性验证及后续任务图扩展方式。
- Codex 官方约定：仓库技能使用 `.agents/skills`，项目规则通过分层 `AGENTS.md` 提供，并采用渐进式上下文加载。

最终选择是自建渐进式“Hydra 精简版”：第一版只建立必要骨架，复杂能力根据真实并发和风险逐步启用。

## 二、目标

1. 使用一套共享规则同时支持 Codex、Claude Code 和 Gemini。
2. 让简单任务可以直接完成，不被完整规格流程拖慢。
3. 让跨领域、高风险或多人并行任务具备可检查的设计、验证和审查记录。
4. 让人工智能代理能够准确找到当前任务的领域所有权、必读文档和验证入口。
5. 使用确定性 C# 工具检查状态、路径和平台适配，避免把关键门禁完全交给提示词。
6. 从第一版固定状态和配置版本接口，使后续增加任务图、工作树池和持续集成门禁时无需整体迁移。

## 三、不在第一版实现的内容

- 不建设看板、常驻同步服务或外部任务平台集成。
- 不实现任务租约、心跳、自动恢复或完整控制器循环。
- 不实现复合仓库工作树池。
- 不接入飞书、Jenkins、GitLab 或其他 Hydra 专用设施。
- 不复制 Hydra 的领域技能和项目规则。
- 不让三个代理平台各自维护独立流程真源。
- 不在第一版自动执行推送、合并、删除或强制归档。

## 四、总体架构

```text
Codex          Claude Code          Gemini
  │                 │                 │
  └────── 各平台薄入口与能力适配 ──────┘
                    │
          共享规则与共享技能真源
                    │
       项目上下文路由与目录所有权
                    │
     直改 / 标准变更 / 受控目标流程
                    │
       Unity、C#、Git 和文档验证工具
```

### 4.1 单一真源

- `.agents/skills`：六个共享技能的唯一人工维护位置。
- `.agents/roles`：探索、实现、审查三个角色说明的唯一人工维护位置。
- `docs/ai`：长期流程规则、权威顺序、平台差异和验证策略。
- `CONTEXT-MAP.md`：五个领域的路由入口。
- 各一级目录的 `CONTEXT.md`：本领域职责、术语、入口和排除项。
- `.lyking-ai.json`：工作流版本、目录和档位配置。

平台目录只保存薄适配文件。适配文件由工具生成并带有真源摘要，不允许手工修改。

### 4.2 规则权威顺序

发生冲突时按以下顺序处理：

1. 用户当前明确要求。
2. 根目录及最近目录的代理规则。
3. 当前代码、测试、配置和生成契约真源。
4. 各领域稳定文档与上下文定义。
5. 当前活动变更记录。
6. 已归档变更、历史记录和外部参考资料。

历史变更不能覆盖当前代码和稳定文档。

## 五、任务档位

### 5.1 直改

适用于同时满足以下条件的任务：

- 不改变用户可见行为、公共接口、网络协议或持久化结构。
- 不需要架构、数据模型或兼容性选择。
- 可以在一次会话内完成。
- 不涉及安全、权限或不可逆操作。

直改不创建变更目录，只要求实施、验证和获得授权后的交付。

### 5.2 标准变更

适用于普通功能、缺陷修复和局部重构。默认工件是：

- `change.md`：问题、结果、验收、范围和风险。
- `evidence.md`：验证命令、关键结果、截图或人工验收入口。

标准变更允许同一代理完成实现和验证。风险信号命中时增加独立审查。

### 5.3 受控目标

命中以下任一信号时使用受控目标：

- 修改 `Client` 与 `Server` 共同依赖的 `Share` 契约。
- 修改存档、网络协议、权限、安全或不可逆数据。
- 一项任务跨越三个以上领域。
- 需要两个以上开发者或代理并行实施。
- 预计跨越多个会话，或者验收项超过八条。
- 需要迁移、兼容、灰度或回滚方案。

受控目标在标准工件之外增加 `design.md`、`plan.md`、任务清单和独立审查报告。

用户可以主动升级档位。普通规模信号可以在记录理由后降级；存档、协议、安全和不可逆数据风险不能直接豁免，只能消除风险、缩小范围或继续使用受控目标。

## 六、状态模型

```text
草稿 → 就绪 → 执行中 → 已验证 → 已归档
              │
              └──→ 已阻塞 ──→ 执行中
```

状态值固定为：

- `draft`：需求或方案尚未确认。
- `ready`：关键决策和验收标准已经确认。
- `active`：正在实施、修复或补充证据。
- `blocked`：存在必须由用户或外部环境解决的阻塞。
- `verified`：所有必需验证和审查已经通过。
- `archived`：交付记录已经冻结。

状态只能沿允许边转换。验证失败时保持 `active` 或进入 `blocked`；不得进入 `verified`。归档后不再修改原记录，后续问题使用新变更或缺陷流程。

## 七、六个核心技能

### 7.1 `lyking-design`

- 输入：用户目标、仓库状态、上下文路由结果。
- 输出：任务档位、关键决策、可观察结果、验收标准和范围。
- 边界：不写实现代码；只有真正互斥的方向才询问用户。

### 7.2 `lyking-implement`

- 输入：已就绪变更或明确直改任务。
- 输出：最小实现、对应测试和更新后的进度。
- 边界：不擅自扩大范围；设计错误必须返回设计阶段。

### 7.3 `lyking-debug`

- 输入：可观察的缺陷、失败测试或异常行为。
- 输出：复现证据、根因、回归验证和最小修复。
- 边界：禁止使用静默降级、无限重试或削弱测试隐藏失败。

### 7.4 `lyking-verify`

- 输入：变更范围和验收标准。
- 输出：新鲜验证证据、失败定位和环境缺口。
- 边界：工作流结构检查不能代替真实 Unity 或 .NET 测试。

### 7.5 `lyking-review`

- 输入：变更目标、累计差异和验证证据。
- 输出：按严重度排序的问题、缺失验证和残余风险。
- 边界：审查者不直接修改被审查实现。

### 7.6 `lyking-deliver`

- 输入：已验证变更、工作区状态和用户授权。
- 输出：本地提交、推送、合并请求或归档结果。
- 边界：推送、合并、删除和强制归档需要明确授权。

技能正文控制在约一百五十行以内。较长规则必须放入按需读取的引用文档。每个技能都明确描述适用场景和不适用场景。

## 八、共享角色

- 探索者：只读定位代码、文档、依赖和影响面。
- 实现者：只修改明确授权的文件范围，并负责对应测试。
- 审查者：只读检查目标、实现、失败路径和验证完整性。

受控目标必须由不同执行上下文完成至少一次审查。平台缺少原生子代理能力时，记录能力缺口并改为独立会话审查，不得启动其他代理命令行冒充原生子代理。

## 十、变更记录格式

`change.md` 第一段保存机器可读 JSON 元数据，其余部分保持中文 Markdown。示例：

```markdown
<!-- lyking-ai
{"schemaVersion":1,"id":"20260906-example","profile":"standard","status":"ready","areas":["Client"],"riskSignals":[]}
-->

# 变更标题

## 解决什么问题

## 完成后应看到什么

## 验收方式

## 范围与非目标

## 风险与回滚
```

C# 工具只提取固定注释块，再使用 `System.Text.Json` 解析内容。元数据与正文同文件保存，避免维护第二份状态文件。

## 十一、确定性工具

`Tool/AiWorkflow` 是独立于 Unity 程序集的 .NET 命令行工具。第一版固定为四个命令：

### 11.1 `route`

根据任务描述、显式影响路径和配置返回：

- 负责领域与相关领域。
- 必读上下文和稳定文档。
- 可能命中的风险信号及匹配依据。
- 建议任务档位。
- 默认排除目录。

没有明确领域时回落到根上下文，不猜测所有权。自由文本匹配只提供候选结果，`lyking-design` 必须结合真实需求完成语义确认；涉及 `Share`、存档、协议和安全目录的硬路径规则由工具机械兜底。

### 11.2 `validate`

检查：

- 配置版本和目录是否有效。
- 变更元数据是否可解析。
- 状态转换是否合法。
- 当前档位的必需工件是否存在。
- 验收、验证和审查门禁是否满足。
- 文档链接、编码和平台适配是否一致。

任何阻塞问题都返回非零退出码。

### 11.3 `sync-adapters`

从共享技能和角色真源生成各平台薄入口，并写入内容摘要。同步过程必须幂等；同一输入重复执行不能产生差异。

### 11.4 `check-workspace`

检查当前分支、脏文件、任务影响范围和危险 Git 条件。它只报告或阻塞，不自动切换分支、暂存文件或执行外部操作。

工具使用本机已经安装的 .NET 10 长期支持版本，并通过 `global.json` 固定具体 SDK。工具项目不进入 Unity 程序集，也不要求 Unity 编辑器启动。

## 十二、平台适配

- `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 都是短入口，只包含平台启动所需规则和共享真源指针。
- Codex 直接发现 `.agents/skills`。
- Claude Code 和 Gemini 使用各自平台目录中的生成适配入口。
- 适配层只表达路径、调用方式和能力差异，不重新定义流程。
- 平台适配不使用符号链接或 Windows 目录联接。
- 平台不支持原生能力时必须显式降级并记录验证缺口。

## 十三、工作流闭环

```text
用户需求
  ↓
平台入口加载共享规则
  ↓
上下文路由：领域、必读文档、风险信号
  ↓
选择直改 / 标准变更 / 受控目标
  ↓
设计或直接实施
  ↓
Unity、C#、资源和文档验证
  ↓
按风险进行独立审查与人工验收
  ↓
获得授权后提交、推送或创建合并请求
  ↓
冻结归档
```

存在未回答的关键决策时禁止进入实施。没有新鲜验证证据时禁止进入 `verified`。界面、美术和交互变化必须通过真实运行截图或人工验收确认。

## 十四、失败处理

- 确定性命令失败时状态不得继续前进。
- 验证失败时必须保留失败证据和原始失败语义。
- 平台能力不足时报告缺口，不伪造成功状态。
- 出现无关脏文件时保持原状；只有文件重叠或交付可能误带时阻塞。
- 适配文件漂移时使用同步命令重建，不逐份手工修补。
- 受控目标的独立审查失败时返回 `active`，修复后重新审查受影响范围。
- 强制归档只能在用户了解所有未验证项并明确接受风险后执行。

## 十五、验证策略

### 15.1 工作流工具

- 单元测试覆盖元数据解析、状态转换、硬路径风险判定、路径安全和适配生成。
- 集成测试在临时 Git 仓库中验证三平台入口、中文路径、不同换行符和脏工作区。
- 生成适配使用确定性快照测试和幂等测试。
- 所有命令以退出码和结构化输出共同表示结果。

### 15.2 游戏项目

- Unity 纯逻辑优先编辑模式测试。
- 场景、生命周期和运行时集成使用运行模式测试。
- 界面、美术和交互保存真实运行截图及人工验收记录。
- `Server`、`Share`、`Tool` 使用各自的 .NET 测试入口。
- 只运行与当前影响面相关的验证；受控目标在交付前增加必要的集成验证。

## 十六、Git 与工作区原则

- 直改可以在当前非受保护分支进行。
- 标准变更和受控目标使用独立任务分支。
- 第一版不自动创建工作树；并行任务出现后再启用普通工作树。
- 只暂存当前变更明确拥有的文件。
- 本地提交可以由已获授权的交付流程执行。
- 推送、合并请求、合并、删除分支和删除工作树必须获得当前会话明确授权。

## 十七、扩展路线

### 17.1 第一阶段：小团队

- 六个技能。
- 三个共享角色。
- 五个领域上下文。
- 三个平台适配。
- 四个确定性命令及测试。
- 直改、标准变更和受控目标三档流程。

### 17.2 第二阶段：并行增加

触发条件是同时存在两个以上相邻文件范围的活动任务，或频繁出现交接与冲突。增加：

- 任务负责人和文件所有权声明。
- 独立审查门禁。
- 普通 Git 工作树支持。
- 活动变更索引和重复任务检测。

### 17.3 第三阶段：大团队

触发条件是稳定存在多团队并行、跨仓库交付或持续集成审计要求。增加：

- 机器可读任务图。
- 工作树池和冲突安全调度。
- 持续集成门禁与证据索引。
- 外部技能版本锁定、项目补丁和同步校验。
- 有界重试、任务恢复和执行指标。

三个阶段沿用相同配置版本、任务档位、状态和变更目录，不进行整体替换。

## 十八、第一版验收标准

1. 三个平台都能从各自入口找到同一套六个共享技能。
2. 平台适配同步连续执行两次时，第二次不产生文件变化。
3. 五类示例任务可以正确路由到对应领域。
4. 相同的显式元数据和影响路径可以按风险规则得到稳定分类，自由文本候选结果必须交给设计技能确认。
5. 非法状态转换、缺少工件和缺少验证证据会返回非零退出码。
6. 工作区检查不会修改分支、暂存区或用户已有文件。
7. 中文路径、简体中文文档和 Windows 换行符通过集成测试。
8. 工作流工具测试全部通过，且项目没有未解释的生成文件或脏改动。
9. 文档明确说明 Unity 测试、.NET 测试和人工验收的边界。
10. 第一版不包含本设计“不在第一版实现的内容”中列出的功能。

## 十九、已接受的主要取舍

- 接受少量平台薄适配文件，换取三个代理平台开箱可发现。
- 接受一个独立 .NET 工具项目，换取跨平台、可测试的确定性门禁。
- 标准变更只保留两份过程文档，避免小团队阶段文档膨胀。
- 受控目标承担更高流程成本，只用于风险或并行确实需要的任务。
- 暂不实现自动任务控制器，避免把尚未出现的组织问题提前固化进系统。
