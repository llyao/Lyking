# Lyking 人工智能工作流总结

本文档汇总 Lyking 多平台人工智能工作流的完整图景，供新成员和代理快速建立整体认知。权威规则以各真源文档为准；发生冲突时按[权威顺序](#权威顺序)处理。

> 设计依据：[2026-09-06-人工智能工作流设计.md](2026-09-06-人工智能工作流设计.md)（已批准）
> 稳定规则：[workflow.md](workflow.md) · [authority.md](authority.md) · [verification.md](verification.md) · [platforms.md](platforms.md)

## 一句话概述

一套共享规则同时驱动 Codex、Claude Code 和 Gemini 三个代理平台：代理先经上下文路由确认领域所有权，再按风险选择直改 / 标准变更 / 受控目标三档流程，沿固定状态闭环推进，关键门禁由确定性 C# 工具（`Tool/AiWorkflow`）机械检查，而不是交给提示词自觉。

## 总体架构

```text
Codex          Claude Code          Gemini
  │                 │                 │
  └────── 各平台薄入口与能力适配 ──────┘
                    │
          共享规则与共享技能真源
                    │
       项目上下文路由与目录所有权
                    │
     直改 / 标准变更 / 受控目标流程
                    │
       Unity、C#、Git 和文档验证工具
```

## 单一真源

| 真源 | 位置 | 说明 |
|---|---|---|
| 共享技能 | `.agents/skills` | 六个 `lyking-*` 技能，唯一人工维护位置 |
| 共享角色 | `.agents/roles` | 探索者、实现者、审查者三个角色说明 |
| 流程规则 | `docs/ai` | 工作流、权威顺序、验证边界、平台适配 |
| 领域路由 | `CONTEXT-MAP.md` + 各一级目录 `CONTEXT.md` | 五个领域的所有权入口 |
| 工作流配置 | `.lyking-ai.json` | 领域、风险规则、档位工件、目录和适配路径 |
| 变更记录 | `docs/changes/active`、`docs/changes/archive` | 活动与归档变更目录 |

平台目录（`.codex/`、`.claude/`、`.gemini/`）只保存由工具生成的薄适配文件，带有真源摘要，禁止手工修改；适配漂移时运行 `sync-adapters` 重建，不逐份修补。

## 工作流闭环

```text
用户需求
  ↓
平台入口加载共享规则（AGENTS.md / CLAUDE.md / GEMINI.md）
  ↓
上下文路由：领域、必读文档、风险信号（route 命令）
  ↓
选择档位：直改 / 标准变更 / 受控目标
  ↓
设计或直接实施
  ↓
Unity、C#、资源和文档验证
  ↓
按风险进行独立审查与人工验收
  ↓
获得授权后提交、推送或创建合并请求
  ↓
冻结归档
```

具体到代理的行为入口：开始任务先读 `CONTEXT-MAP.md` 和受影响目录最近的 `CONTEXT.md`，按需加载对应 `lyking-*` 技能，用 `route` 确认领域和风险，再确定档位。

## 任务档位

| 档位 | 使用条件 | 必需工件 |
|---|---|---|
| 直改 | 无可见行为、公共接口、协议、持久化、安全和架构选择变化；单会话可完成 | 不建变更目录 |
| 标准变更 | 普通功能、缺陷和局部重构 | `change.md`、`evidence.md` |
| 受控目标 | 共享契约、存档、协议、安全、不可逆数据、至少三个领域、多人并行、跨会话、超过八条验收或迁移兼容回滚 | 标准工件及 `design.md`、`plan.md`、`tasks.md`、`review.md` |

档位调整规则：

- 用户可以主动升级档位。
- 普通规模信号只有说明理由后才允许降级。
- 协议、存档、安全、不可逆风险不能直接豁免，只能消除风险、缩小范围或继续使用受控目标。
- 命中风险信号的标准变更仍需独立审查。

模板位于 `docs/ai/templates/`（`change.md`、`design.md`、`evidence.md`、`plan.md`、`tasks.md`、`review.md`）。

## 状态模型

```text
草稿 → 就绪 → 执行中 → 已验证 → 已归档
              │
              └──→ 已阻塞 ──→ 执行中
```

| 状态 | 值 | 含义 |
|---|---|---|
| 草稿 | `draft` | 需求或方案尚未确认，关键决策未确认时保持在此 |
| 就绪 | `ready` | 关键决策和验收标准已确认 |
| 执行中 | `active` | 正在实施、修复或补充证据；验证失败时保持或转入阻塞 |
| 已阻塞 | `blocked` | 存在必须由用户或外部环境解决的阻塞 |
| 已验证 | `verified` | 所有必需验证和审查已通过；没有新鲜证据不得进入 |
| 已归档 | `archived` | 交付记录已冻结，后续问题创建新变更 |

状态只能沿允许边转换，不得跳边；状态转换由调用者修改元数据后用 `validate --transition 起点:目标` 检查，失败必须恢复状态。

## 六个核心技能

| 技能 | 输入 | 输出 | 边界 |
|---|---|---|---|
| `lyking-design` | 用户目标、仓库状态、路由结果 | 档位、关键决策、验收标准和范围 | 不写实现代码；只有真正互斥的方向才询问用户 |
| `lyking-implement` | 已就绪变更或明确直改任务 | 最小实现、对应测试和进度更新 | 不扩大范围；设计错误返回设计阶段 |
| `lyking-debug` | 可观察缺陷、失败测试或异常 | 复现证据、根因、回归验证和最小修复 | 禁止静默降级、无限重试或削弱测试隐藏失败 |
| `lyking-verify` | 变更范围和验收标准 | 新鲜验证证据、失败定位和环境缺口 | 结构检查不能代替真实测试 |
| `lyking-review` | 变更目标、累计差异和证据 | 按严重度排序的问题、缺失验证和残余风险 | 审查者不直接修改被审查实现 |
| `lyking-deliver` | 已验证变更、工作区状态和授权 | 提交、推送、合并请求或归档结果 | 推送、合并、删除和强制归档需要明确授权 |

技能正文控制在约一百五十行以内，较长规则放入按需读取的引用文档。

## 共享角色

- **探索者**：只读定位代码、文档、依赖和影响面。
- **实现者**：只修改明确授权的文件范围，并负责对应测试。
- **审查者**：只读检查目标、实现、失败路径和验证完整性。

受控目标必须由不同执行上下文完成至少一次独立审查；平台缺少原生子代理能力时记录缺口并改为独立会话审查，不得启动其他平台命令行冒充原生子代理。

## 变更记录格式

`change.md` 第一段保存机器可读 JSON 元数据，其余部分保持中文 Markdown：

```markdown
<!-- lyking-ai
{"schemaVersion":1,"id":"20260919-example","profile":"standard","status":"ready","areas":["Client"],"paths":["Client/Feature/"],"riskSignals":[]}
-->
```

- `id`：日期-短名，如 `20260919-hydra-game-framework`。
- `paths`：本次变更允许触及的仓库相对路径；执行工作区检查时缺少范围必须由调用者显式提供。
- `areas` 与 `riskSignals`：语义范围和命中的风险信号。
- 元数据与正文同文件保存，不维护第二份状态文件。

当前活动变更示例：`20260906-ai-workflow-v1`（工作流第一版落地）、`20260919-hydra-game-framework`（通用游戏框架，受控目标）。

## 确定性工具

`Tool/AiWorkflow` 是独立的 .NET 10 命令行工具（不依赖 Unity 编辑器），从仓库根目录运行：

```powershell
dotnet run --project Tool/AiWorkflow/Lyking.AiWorkflow.csproj -- <命令>
```

| 命令 | 职责 | 边界 |
|---|---|---|
| `route` | 根据任务描述和显式路径返回领域、必读上下文、风险信号和建议档位 | 只根据显式路径确定领域；自由文本只返回候选，由设计阶段语义确认；无法确定时停留根上下文 |
| `validate` | 检查配置、元数据、状态转换、必需工件、门禁、链接和适配一致性 | 只读；不能证明测试真的运行过，不替代证据新鲜度核验 |
| `sync-adapters` | 从共享真源重建三平台适配并写入摘要 | 只写受管平台文件；拒绝覆盖非受管同名文件；幂等 |
| `check-workspace` | 只读报告 Git 分支、脏文件和影响范围 | 不自动切分支、暂存或执行外部操作；范围外已暂存文件阻塞 |

退出码：`0` 成功、`2` 参数无效、`3` 输入无效、`4` 验证失败或适配漂移、`5` Git 工作区阻塞、`10` 内部错误。

工具自身由 `dotnet test Tool/AiWorkflow/Tests/Lyking.AiWorkflow.Tests.csproj` 验证，覆盖元数据解析、状态转换、硬路径风险判定、路径安全和临时 Git 仓库集成测试。

## 平台适配

| 平台 | 规则入口 | 技能发现 | 生成角色 |
|---|---|---|---|
| Codex | `AGENTS.md` | `.agents/skills` | `.codex/agents/*.toml` |
| Claude Code | `CLAUDE.md` | `.claude/skills`（生成薄适配） | `.claude/agents/*.md` |
| Gemini CLI | `GEMINI.md` | 原生别名 `.agents/skills` | `.gemini/agents/*.md` |

- 适配层只表达路径、调用方式和能力差异，不重新定义流程。
- 只读角色按平台限制工具权限（如 Claude 只读角色限制为 `Read, Grep, Glob`）。
- 技能 SHA-256 按原始字节计算，相同输入重复同步必须内容不变；`.gitattributes` 对真源和生成适配固定 LF。
- 禁止符号链接和目录联接。
- 本地格式检查不能代替实际发现验收；能力不足时记录缺口，不伪造成功。

## 验证边界

验证对应当前代码、环境和验收声明；证据包含日期、实际命令、退出码、测试通过与失败数量及关键输出，旧日志不能代替修改后的验证。

| 范围 | 验证入口与证据 |
|---|---|
| 工作流工具 | `dotnet test Tool/AiWorkflow/Tests/Lyking.AiWorkflow.Tests.csproj` |
| Unity 纯逻辑 | 编辑模式测试；新增 Unity 工程后在领域上下文记录真实命令 |
| 场景、生命周期、运行时集成 | 运行模式测试，必要时记录运行条件和复现步骤 |
| 服务端 | 对应 .NET 测试、集成和部署配置检查 |
| 共享契约 | 客户端与服务端共同编译、协议和存档兼容验证 |
| 美术、界面与交互 | 当前版本真实运行截图或明确人工验收记录 |

结构检查只能验证工件、状态、编码、链接和适配一致性，不能验证测试日志真实性、证据与代码的新鲜对应或真人审查身份；声明 `verified` 前由操作者核对，有缺口时记录并保持 `active`。当前游戏目录尚无可执行工程，不虚构 Unity 或业务测试命令。

## 权威顺序

从高到低解决冲突：

1. 用户当前明确要求。
2. 根目录及最近目录的代理规则。
3. 当前代码、测试、配置和生成契约真源。
4. 领域稳定文档与上下文。
5. 当前活动变更记录。
6. 已归档变更、历史记录和外部参考资料。

历史记录不能覆盖当前代码和稳定规则。

## 失败处理与交付边界

- 确定性命令失败时状态不得前进；验证失败保留原始失败语义，修复后重新取证。
- 无关脏文件保持原状；范围外已暂存文件阻塞交付，只暂存当前变更拥有的路径。
- 独立审查失败返回 `active`，修复后重新审查受影响范围。
- 强制归档只能在用户了解所有未验证项并明确接受风险后执行。
- 本地提交服从已有授权；推送、合并、删除和强制归档需要当前会话明确授权。
- 直改可在当前非受保护分支进行；标准变更和受控目标使用独立任务分支。

## 第一版边界与扩展路线

第一版明确不包含：看板、常驻同步服务、外部任务平台集成、任务租约/心跳/自动恢复、工作树池、飞书/Jenkins/GitLab 集成、自动推送合并删除。

扩展路线沿用相同配置版本、档位、状态和变更目录，不做整体替换：

1. **第一阶段（当前）**：六技能、三角色、五领域上下文、三平台适配、四个确定性命令、三档流程。
2. **第二阶段（并行增加）**：触发条件是两个以上相邻文件范围的活动任务并存或频繁交接冲突；增加文件所有权声明、独立审查门禁、普通工作树支持、活动变更索引。
3. **第三阶段（大团队）**：触发条件是多团队并行、跨仓库交付或持续集成审计；增加机器可读任务图、工作树池、持续集成门禁与证据索引、外部技能版本锁定、有界重试与执行指标。
